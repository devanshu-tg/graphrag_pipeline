Read strict pass, not the judge. Strict means the answer set matches gold exactly — no partial credit. The judge is a lenient second opinion and it flatters the baseline: Basic RAG scores 62.3% judged but only 26/50 exactly right. Where the two disagree, strict is the number of record.
The budgets are deliberately unequal, in the baseline's favour. GraphRAG reads 3 chunks; Basic RAG reads 10. Ten is where the reranked baseline scores best — cutting it to 3 drops its retrieval hit@k from 82.5% to 75.0% — so it is shown at its strongest while GraphRAG reads less. Not measured: the baseline end-to-end at a 3-chunk budget.
1,185 of GraphRAG's 2,733 tokens are the planner call — 43% of its spend, and a fixed cost that does not shrink with the chunk budget. That is the floor on the token claim, not a number to leave out.
BERTScore is shown and is not the number of record. Here it happens to rank the arms correctly (0.852 / 0.934 / 1.000). On the SEC set it put LLM-only above Basic RAG (0.839 vs 0.830) while LLM-only got 5 of 50 right — it rewards fluent wrong answers. A metric that only works when you already know the answer is not evidence.

Run-to-run variance

The headline figures above come from a single run, and the page says so. We have two independent runs at a neighbouring configuration (10-chunk budget rather than 3): GraphRAG scored 49/50 and 50/50, with tokens 5,260 and 5,250. So run-to-run movement is about one question. That is not the same as three replicates of the published config, and it is not reported as if it were.

How it works

No extraction. The metadata already carried the relations.

The expensive part of most GraphRAG builds is LLM entity extraction. This corpus did not need it: every document already names its author, its channel, its project. The graph was built from fields, at zero LLM cost and 100% coverage.

1. SOURCE                     20,182 documents  ->  73,613 chunks
   Confluence pages · Jira tickets · GitHub PRs · Slack messages
   employee_directory.yaml  ->  the org chart (the one authored input)
   The company is FICTIONAL. Nothing here is answerable from model memory.
                                     |
2. GRAPH CONSTRUCTION — metadata, not extraction
   author / channel / department / team / repo fields already present
   ->  128,282 provenance edges, 11 relation types, $0 in LLM calls
   participated_in 88,188 · has_label 11,546 · in_channel 11,146
   authored 6,645 · in_team 5,377 · reports_to 160
                                     |
3. TIGERGRAPH SAVANNA — graph AND vector store, for BOTH retrieval arms
   Vertices: Person, Document, Channel, Department, Team, Repo,
             Chunk(text, embedding vector[384, cosine])
   Installed queries: vector_search_lite(query,k) · hop_<rel>_out(seeds)
                      intersect_channels(a,b) · dept_in_channel(d,c)
                                     |
                    +----------------+----------------+
                    |                |                |
4A. LLM ONLY     4B. BASIC RAG            4C. GRAPHRAG
    no retrieval     bge-small embed           schema router -> plan
    the leak gate    TG vector top-k=10        traverse TG (1-3 hops)
                     cross-encoder rerank      UNION with vector top-k=3
                     (200-candidate pool)      provenance-sentence context
                     -> answer                 -> answer
                    |                |                |
                    +----------------+----------------+
                                     |
5. SCORING   strict set match (exact, no partial credit)  <- number of record
             blind judge, different model family          <- second opinion
             BERTScore                                    <- shown, not trusted
             hit@k against expected_doc_ids               <- retrieval, isolated
The baseline retrieves through TigerGraph too. Both arms use the same vector store, the same embedder and the same corpus, so the only difference between them is whether the graph is consulted. And the baseline is the reranked one — a cross-encoder over a 200-candidate pool, which took it from 0.30 to 0.53 set-F1 at the same token cost. Beating a weak baseline would prove nothing.

Limits

What this does not show.

All 50 enterprise questions are relationship traversals — the shape a graph is built for. The answer key was computed BY traversal and then independently re-derived from 20,182 raw documents (30/30) to check it was correct — but correct is not the same as unbiased, and the question set favours the graph by construction. The SEC tab is the honest counterweight: same architecture, and it loses single-fact lookup by 38 points.
Chunk overlap is 0, not the configured 200. The corpus builder ignores the setting, so facts spanning a chunk boundary are unreachable — and this penalises the baseline only, since GraphRAG does not read chunks on a graph route. An asymmetry that favours the system under test, disclosed rather than fixed.
Single run for the published configuration, no mean ± std. Two runs exist at a neighbouring config and moved by one question. Ablations (graph off / router off / compression off) and a citation-validity judge are not run — and citations are therefore not evidence anywhere on this page: LLM-only emitted Citations: [1],[2],[3] having been given no context at all.
Every figure on this page is computed from results/enterprise/*.jsonl by demo/build_report.py at build time. None are typed by hand.
